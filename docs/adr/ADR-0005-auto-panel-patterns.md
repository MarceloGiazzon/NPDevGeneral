# ADR-0005 Auto-Panel Patterns

## Status
Proposed - 2026-07-11

## Context

[ADR-0004](ADR-0004-aggregate-workbench.md) defined the Aggregate Workbench: a generated
multi-region editor over a declared aggregate. In building it we recognized a missing **middle tier**
in NPDev's authoring surface. Today there are two poles:

- **Default** — what the generator emits automatically from a concept (a basic list/form), and
- **Free panel** — a fully hand-authored `panel{}` / `workbench{}`.

Most real business screens sit between these. GeneXus solves this with its **Pattern object**
("Work With"): a slim, concept-bound declaration that expands into a coordinated set of wired
objects — Selection (list), Prompt (modal select), View (detail), and the Transaction (form) with
Sections for subordinate levels. The pattern reads defaults from the transaction's attributes, so
the declaration is small; you add configuration only to override or enrich.

NPDev needs the same intermediate tier. Without it, every non-trivial screen forces authors down to
the free-panel level, and the Aggregate Workbench risks being a bespoke one-off rather than the top
of a reusable ladder.

## Decision

Introduce the **AutoPanel** (an "auto panel" / pattern): a slim, concept- or aggregate-bound
declaration that the generator **expands** into a coordinated, fully-wired set of surfaces. This
establishes a three-tier authoring model.

### Three tiers
| Tier | Author writes | Generator produces |
|---|---|---|
| Default | nothing (just the concept) | basic list + form |
| **AutoPanel** | a slim `autoPanel{}` bound to a concept/aggregate | Selection + Prompt + Detail + Transaction (+ Sections), fully wired |
| Free panel / workbench | full `panel{}` / `workbench{}` | exactly as declared |

### Surfaces (the expansion targets)
An AutoPanel expands into these generated surfaces (a subset is selectable via `surfaces`):
- **Selection** — filtered list + grid (the "Work With" list).
- **Prompt** — modal single/multi select for choosing rows (foreign-key picking); the
  `SelectorGrid` from ADR-0004.
- **Detail** — read-only view of one record.
- **Transaction** — create/update form. Single-level for a concept; **for an aggregate-bound
  AutoPanel the Transaction *is* the Aggregate Workbench** (Header + Grid + Band sections).
- **Sections** — tabs/subordinate grids for owned child collections.

### Relationship to ADR-0004
The Aggregate Workbench is not superseded — it is **subsumed as the Transaction surface of an
aggregate-bound AutoPanel**. The `aggregate` primitive (data shape) and the Region taxonomy
(Header/Grid/Band/SelectorGrid/ActionRail) remain exactly as defined; they become the AutoPanel's
**expansion vocabulary**. `workbench{}` and `panel{}` remain as the **per-surface escape hatch**
(`"transaction": { "panel": "CustomEditor" }`).

### Defaults from the concept
Expansion reads from the concept so declarations stay slim: fields → form inputs & grid columns
(honoring the widget/datatype system); id field → route params & prompt return value; bonds → FK
prompts and nested sections (owned bonds → subordinate grids); ui labels → captions;
required/validation → form validation. `{ "concept": "Cliente" }` alone yields a full CRUD applet.

### Wiring (generated by core)
The generator wires routes per surface, workspace-menu nav entries, prompt buttons on FK fields
across all generated forms, permissions from concept/pack defaults, and aggregate load/commit for
multi-level transactions.

### Overridability
Every surface is individually overridable: point it at a free panel/workbench, or bind the whole
AutoPanel to an aggregate to make its Transaction multi-level. This is the sanctioned escape hatch
and the promotion path — a repeatedly hand-authored surface pattern becomes an AutoPanel default.

## Consequences

- The AutoPanel becomes the **primary authoring surface**; default and free-panel remain the poles.
- Value lands earlier and everywhere: a single-concept AutoPanel is broadly useful before the hard
  multi-level work is complete. The WMS editor becomes the top rung of a ladder every app climbs.
- The implementation plan is re-sequenced around AutoPanel expansion (see
  [AGGREGATE_WORKBENCH_PLAN](../architecture/AGGREGATE_WORKBENCH_PLAN.md), revised): single-concept
  expansion first (Selection/Detail/Transaction/Prompt), then multi-level (Sections→Bands over an
  aggregate) reusing the Workbench regions.
- Risks: expansion defaults must be predictable and overridable, or authors lose trust; the
  concept→surface mapping must honor the existing widget/bond systems rather than reinventing them.
- ADR-0004 remains in force for the aggregate + workbench substrate; this ADR reframes the surface
  above it. Future changes to the AutoPanel contract update this ADR.
