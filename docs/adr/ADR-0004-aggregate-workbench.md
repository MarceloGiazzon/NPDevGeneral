# ADR-0004 Aggregate Workbench

## Status
Proposed - 2026-07-11

## Context

The WMS receiving/shipping editors (`NovoCentroExpedicao`, `NovoCentroRec` in the
GeneXus source `D:\WorkSpace\WmsOffice\OriginalArtifacts\WmsLabs_Mod_GX17.xml`) are the most
structurally complex screens we have attempted to reproduce with NPDev. Each is a single page
that edits a **composition tree** — an aggregate root plus nested owned collections — with:

- three vertically stacked regions, each with its own independent edit / undo / save buffer;
- a repeating "band" (one card per parent row) whose innermost node holds **two parallel
  editable grids** (Expedicao: ORIGEM + DESTINO; Recebimento: DESTINO only);
- **live client-side computed cells** (`Total = Pos*CxPad + CxAvulsas`, Sub-Total, Máximo,
  Pendente Origem) that recompute on keystroke ("ReCalcular Saldos");
- a **stage machine** (`Estágio`: PreDemanda → Demanda Gerada → Endereçado → Movimentação
  Confirmada → Saída Confirmada) gating which regions/actions are live;
- server **recompute/allocate** operations (Gerar Demanda, Confirmar Movimentação);
- modal multi-select pickers ("Seleciona Ruas") that return rows into a grid.

The two list screens (`TelaExpedicao`, `TelaRecebimento`) and the Level-1 header are already
expressible on today's Panel primitive. The 3-level editor is **not**. Rather than hand-build one
bespoke screen, we treat this as the forcing function to define a reusable platform primitive: the
same shape powers any master-detail-detail business screen (orders/lines, invoices, BOMs,
production plans). WMS is the conformance test, not the deliverable.

Reference analysis and the 15 source screenshots:
`D:\WorkSpace\WmsOffice\OriginalArtifacts\Galery\multi-level`.

## Decision

Introduce the **Aggregate Workbench**: a generated multi-region editor over a declared aggregate,
built from five composable layers. The design maximizes what is generated by default and confines
bespoke code to named extension seams.

### L1 — `Aggregate` model primitive
Promote composition to a first-class model concept: a root concept plus **owned** child
collections, with ownership, ordering, and edit-cohesion (children load / draft / validate / commit
as one unit). This extends [bonds](#) (FK edges) with ownership semantics and aligns with the
Box/Object/Truth cluster. Declaring the tree is what lets the generator emit everything below.

### L2 — Region component taxonomy
A workbench is a stack of typed regions, each generated from a node of the aggregate tree:
`HeaderRegion` (form over root), `GridRegion` (declared-column editable grid over an owned
collection, row-select emits context downward), `BandRegion` (repeating card, one per parent row,
hosting 1..N child grids), `SelectorGrid` (modal filtered multi-select returning rows),
`ActionRail` (left action strip generated from a region's declared actions).

### L3 — Two-tier reactivity
- **Tier A (client):** pure CEL computed fields over row/aggregate scope, evaluated reactively in
  the generated bundle. Reuses the `expression-cel` language; adds a client evaluator. No round-trip.
- **Tier B (server):** procedure-over-aggregate. Reads the draft tree, runs a **procedure**
  (procedures may loop; flows may not), returns a patched draft. This is the sanctioned seam for
  allocation math (Gerar Demanda, recompute saldos from stock).

### L4 — Declared lifecycle
A state machine (states + transitions + per-state `{editableRegions, allowedActions}`) bound to the
existing FlowEngine. Status chip, region enablement, and action-rail gating are generated from it.

### L5 — Extension slots (the wiring)
The generator emits scaffold + named slots; the author fills slots; a slot filled the same way
across apps is promoted to a generator default. Slot kinds: `procedureSlot` (actions),
`computeSlot` (columns), `validationSlot` (server rules — Máximo, "Endereçamento OK!"),
`layoutSlot` (swap a generated region for a hand-authored panel, keeping data wiring).

### Runtime contracts
- **Client:** a reactive normalized aggregate store in the emitted bundle — draft tree, registered
  computed fields, **per-region dirty tracking** (this is what gives each level its own
  Modo Edição / Desfazer / Salvar), and an action dispatcher. Emitted by templates only; never
  post-gen patched (`npdev-generated/` is hash-guarded).
- **Server:** a kernel `AggregateController` beside `GeneratedCrudRuntimeSupport`:
  `load(rootId)→tree`, `patch(draft)→validated`, `invoke(procedure, draft)→tree`,
  `commit(draft)→persist with cascade` (reuses bond `onDelete`/ownership).

### Default / configured / bespoke split
~80% generated from the model, ~15% author-configured via DSL knobs (filter sets, column
order/width, computed expressions, lifecycle states, action composition), ~5% bespoke procedures
(allocation, confirm rules) reached only through slots.

### Delivery phases (each ships a named core primitive; WMS is its proof)
- **P0** `Aggregate` model primitive (schema in all 4 mirrors + compiler + nested read API).
- **P1** `HeaderRegion` + `GridRegion` + default generation (Levels 1–2).
- **P2** Tier-A computed columns + client reactive store.
- **P3** Row add/delete + `SelectorGrid` picker (closes open gaps #13/#14).
- **P4** `BandRegion` (2nd nesting, parallel grids) — the hardest primitive.
- **P5** Lifecycle state machine + action-rail gating.
- **P6** Procedure-over-aggregate + commit boundary (Tier B).
- **P7** Recebimento via the same workbench, different aggregate shape (generality proof).
  Reports / document attach deferred (file-upload is a known boundary).

## Consequences

- NPDev graduates from a form/grid generator to an **aggregate-application generator**; the
  workbench becomes a new page kind alongside PAGE/Panel.
- The reactive draft store + procedure-over-aggregate boundary also underpins optimistic/offline
  editing and lets the AI authoring bridge emit whole workbench declarations; because every cell
  traces to a declared expression, generated workbenches are explainable by construction.
- Known platform boundaries constrain the design: flows have no loop step (allocation lives in
  procedures), capabilities are pure functions (recompute is a procedure-over-aggregate), no
  file-upload (document attach deferred), and the generated bundle is hash-guarded (reactivity must
  be template-emitted).
- P0 and P4 carry the architectural risk. P4 (BandRegion + reactive store) is validated by a
  throwaway spike before the schema shape is committed. Evidence lives outside the repo per policy.
- Supersedes the ad-hoc "just reproduce the panels" approach. Future changes to the workbench
  contract should update this ADR.
