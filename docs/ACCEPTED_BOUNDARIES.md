# Accepted Boundaries — what NPDev deliberately does not do

> **Written:** 2026-07-25 · Verified against the live tree. **Re-verified and reclassified 2026-08-04
> (REG-135)**: every row below was traced to its real enforcing code (or confirmed to have none),
> not just read by its title.
>
> **These are not gaps, not bugs, and not a backlog.** Each is a conscious design decision with a stated
> reason, a workaround, and a named trigger that would justify revisiting it. Treating one of these as a
> "TODO" and "fixing" it without hitting its trigger is how a stable subsystem gets destabilised.
>
> **How to use this document:** before filing an item as a gap, check here. If it is listed, the question
> is not *"why isn't this done?"* but *"has its revisit trigger fired?"*
>
> **This document is user-facing** — real product limits an app author or end user can hit while
> building or running an app. Six rows that used to live here (B21-B26) were about NPDev's OWN CI,
> corpus layout, and test-coverage practices, not the product — moved to
> `docs/PROJECT_POSTURE.md` (REG-135 step 2). A boundary marked **HITTABLE** below fires a real
> diagnostic (rendered as `LIMIT`, not `ERROR`, when the mechanism reaches it — see
> `ledger/boundaries/*.yml` for which ones are wired to a `boundaryId` today); one marked
> **POSTURAL** is a real, documented limit with no diagnostic to fire.

| B13 | **Conversion hooks are SQL-only** — no Java `DataMigrationHook`. **A declarative vocabulary now exists BESIDE the raw-SQL path** (S7 Phase B, 2026-08-03; widened to 5 ops — S8 W1.2, 2026-08-04): `conversions[]` (`copy`/`split`/`lookup`/`merge`/`convert`) lets an author express a schema-evolution data migration without writing SQL by hand; the compiler resolves every `concept`/field reference against the real model graph (an unresolvable one is a named compile error, never a silently-dropped conversion) and the generator compiles each entry to the SAME `db/conversion-hooks/<id>/{hook.json,convert.sql}` shape `ConversionHookRunner` already executes — one execution path, not two. Declarative vocabulary: an in-place existing-column retype becomes a real, frequent need — would require plumbing a "previous model version" input into the generator (or a live-DB-aware claim, a bigger change) before it could reuse this same claim-matching mechanism | `ConversionHookRunner` javadoc, `NPDevGenerator/generator/.../dbconfig/ConversionHookEmitter.java`, `NPDevContract/schemas/model.schema.json` `$defs/conversion`, `NPDevSamples/dsl-conformance-max` (corpus witness, all 5 ops) |

## 3. Reading these correctly

Three of these boundaries exist because **the safe answer is to refuse rather than guess**: B1 (rename),
B4 (concurrency), B5 (schema-ahead). That is the schema engine's governing instinct — when intent cannot
be recovered from shape, stop and ask a human. Several others (B3, B12, B13) exist because **the
conservative half of a feature is worth shipping without the dangerous half**.

If you are about to remove one of these, the question to answer in writing is: *what new information do
we have that the original decision lacked?* If the answer is "none, it just feels incomplete" — leave it.
