# Accepted Boundaries — what NPDev deliberately does not do

> **Written:** 2026-07-25 · Verified against the live tree.
>
> **These are not gaps, not bugs, and not a backlog.** Each is a conscious design decision with a stated
> reason, a workaround, and a named trigger that would justify revisiting it. Treating one of these as a
> "TODO" and "fixing" it without hitting its trigger is how a stable subsystem gets destabilised.
>
> **How to use this document:** before filing an item as a gap, check here. If it is listed, the question
> is not *"why isn't this done?"* but *"has its revisit trigger fired?"*

---

| B13 | **Conversion hooks are SQL-only** — no Java `DataMigrationHook`. **A declarative vocabulary now exists BESIDE the raw-SQL path** (S7 Phase B, 2026-08-03; widened to 5 ops — S8 W1.2, 2026-08-04): `conversions[]` (`copy`/`split`/`lookup`/`merge`/`convert`) lets an author express a schema-evolution data migration without writing SQL by hand; the compiler resolves every `concept`/field reference against the real model graph (an unresolvable one is a named compile error, never a silently-dropped conversion) and the generator compiles each entry to the SAME `db/conversion-hooks/<id>/{hook.json,convert.sql}` shape `ConversionHookRunner` already executes — one execution path, not two. Every generated hook is idempotent BY CONSTRUCTION (`ADD COLUMN IF NOT EXISTS` + `UPDATE … WHERE <col> IS NULL` + a re-runnable `ALTER COLUMN … SET NOT NULL`), turning B12's "write every hook idempotent" discipline into a compiler guarantee for this path. Scope, deliberately: v1 covers a target field that is BRAND NEW in this model version (`ADD_REQUIRED_COLUMN`) — a field that already exists and merely needs data migrated converges as SAFE_ADDITIVE/NEEDS_BACKFILL with no residual diff item for a hook to claim, so it never reaches this mechanism at all (use `defaultExpression`/`ExpressionBackfillPreview` — B2 above — instead). A row a conversion cannot populate (e.g. `split` with no space in the source value, `merge` with either source field NULL) is left NULL and the closing `SET NOT NULL` then fails the boot loudly with the engine's own error, never a silent partial conversion. **`merge` and `convert` (S8 W1.2, roadmap deferred item #4) reuse this SAME `ADD_REQUIRED_COLUMN` shape, not a new one**: `merge` is `split`'s inverse (N declared source fields, `CONCAT`-ed with an author-declared separator, into one new field); `convert` is `copy` with an explicit `CAST` to the target field's own declared type instead of a bare assignment — a source value the target type cannot represent fails the `CAST` itself (a real `SQLException`, rolling back the whole hook transaction) rather than leaving a partially-typed column. Neither op has (or needed) a `toType`/separate-type property: `convert`'s target type is `to`'s own already-compiler-resolved declared field type, the same information a second `toType` property would just duplicate and risk drifting from. **Deliberately NOT built**: retyping an EXISTING field's OWN column IN PLACE (the plan's originally-sketched `convert` shape, `{"op":"convert","concept":"Order","field":"total","toType":"decimal"}`) — traced during S8 W1.2 to a real architectural wall, not a choice: `ConversionHookRunner.run()` only ever selects a hook whose `claims` intersect the LIVE schema diff's unresolved items, and an in-place retype's correct claim shape is `NARROW_TYPE:table:column:fromType:toType` (`SchemaDeltaItem.NarrowType`), which needs the column's CURRENT live type — unknowable at generation time (the generator compiles one model version, with no "previous version" input). `ADD_REQUIRED_COLUMN:table:column` (a MISSING column) needs no such foreknowledge, which is exactly why `copy`/`split`/`lookup` — and now `merge`/`convert` — all target brand-new fields | **Java hooks remain out of scope, unchanged**: code-bearing objects belong to the ADR-0003 track, with its own sandboxing/versioning story; running author-supplied Java against production data during boot is a materially different and more dangerous risk than compiling a closed, reviewable op vocabulary to SQL, and shipping one casually would pre-empt ADR-0003's design. For the covered case, declare a `conversions[]` entry instead of hand-writing `convert.sql`; for a migration the five ops genuinely cannot express (in particular: retyping an EXISTING field's column in place, see the why-column above), fall back to an operator-authored SQL hook (`definition/migrations/<ordinal>-<slug>/`) as before | Java hooks: ADR-0003 code-bearing-objects lands. Declarative vocabulary: an in-place existing-column retype becomes a real, frequent need — would require plumbing a "previous model version" input into the generator (or a live-DB-aware claim, a bigger change) before it could reuse this same claim-matching mechanism | `ConversionHookRunner` javadoc, `NPDevGenerator/generator/.../dbconfig/ConversionHookEmitter.java`, `NPDevContract/schemas/model.schema.json` `$defs/conversion`, `NPDevSamples/dsl-conformance-max` (corpus witness, all 5 ops) |

## 4. Reading these correctly

Three of these boundaries exist because **the safe answer is to refuse rather than guess**: B1 (rename),
B4 (concurrency), B5 (schema-ahead). That is the schema engine's governing instinct — when intent cannot
be recovered from shape, stop and ask a human. Several others (B3, B12, B13) exist because **the
conservative half of a feature is worth shipping without the dangerous half**.

If you are about to remove one of these, the question to answer in writing is: *what new information do
we have that the original decision lacked?* If the answer is "none, it just feels incomplete" — leave it.
